# Demo recording guide

The demo data is synthetic: `demo/project/` (a small checkout app) and `demo/logs/production_sample.log` (generated by `python scripts\generate_demo_log.py`,
which looks up the real line numbers in the project, so every stack trace points at real code). **No recording exists yet**, so the README links none.
Only record the real application; never fake or mock up a GIF.

## 1. Prepare (5 minutes)
```powershell
cd path\to\bug-report-log-analyzer
.venv\Scripts\activate
python scripts\demo_check.py                 # data, port, and the numbers you should see on screen
python scripts\demo_check.py --reset-history # optional: also empties the History file (deletes saved runs)
```
Checklist before recording:
- Close other windows and tabs; turn on Windows Focus Assist so notifications do not pop up.
- Browser at 100% zoom, window about 1280x720, bookmarks bar hidden. Use the demo data only.
- Start the app without the toolbar: `streamlit run app.py --client.toolbarMode minimal` (skip this flag if your Streamlit version rejects it).
- Keep the mode rule-based for the recording. An LLM adds model latency that varies by machine and was not measured; if you use one, rehearse it.
- Open the app on the **Dashboard** with no run loaded (restart the app if needed).

## 2. The 60-second plan
| Time | Segment | Do | Say |
|---|---|---|---|
| 0:00–0:05 | Open the dashboard | The app is already open on the **Dashboard** (empty state). Keep the mouse still. | This tool turns a messy log into evidence and a bug report. |
| 0:05–0:10 | Load the demo | Click **Log Analyzer** in the sidebar, click **Load demo**, and open the preview. | A synthetic production log: thousands of lines, errors buried in noise. |
| 0:10–0:20 | Analyze the log | Click **Analyze**. The progress bar runs and the result counts appear. Then click **Investigate error groups →**. | One click parses, groups the errors, finds the code and builds the analysis. All numbers are measured. |
| 0:20–0:30 | Show the detected incident | On the Error Groups page G001 is selected: point at its severity, its count and the timeline. | Thousands of events collapse into a few incidents. G001 is a burst of database timeouts. |
| 0:30–0:40 | Show the root cause | Click **Open root-cause analysis →**, show **1 · Observed evidence**, then click **2 · Hypothesis**. | Measured evidence stays separate from the hypothesis, which is labeled as not confirmed. |
| 0:40–0:50 | Show the source code | Click **View code →**. The verified snippet is already open; point at the verified badge. | The real file and line, verified against the stack trace. |
| 0:50–1:00 | Generate the Jira report | Click **Bug Report** in the sidebar, tick **I have reviewed this report**, show **Copy for Jira**, click **⬇ Markdown**. | A Jira-ready draft, reviewed by a human, ready to copy or download. |

Timing notes: the analysis itself finishes in a fraction of a second on the demo, so the progress bar is brief. Use that segment to point at the counts.
Rehearse with the timer: `python scripts\demo_rehearsal.py` (it shows each cue, then compares your pace with the plan).

Honest wording while narrating: the analysis is rule-based; an optional local LLM can rewrite the hypothesis. Do not say "AI-powered" unless the recording shows a model run.

## 3. Record on Windows (all free)
| Tool | How |
|---|---|
| Xbox Game Bar | Press **Win+G**, or **Win+Alt+R** to start and stop recording the focused browser window. The MP4 is saved in `Videos\Captures`. |
| ScreenToGif | Free, open-source recorder with a built-in editor that records straight to GIF. Good for trimming and lowering the frame rate. |
| OBS Studio | Free; best control over resolution and cursor highlighting. |

Do two rehearsals, then record three takes and keep the best.

## 4. Make the GIF
If you recorded MP4 and have `ffmpeg` installed (for example `winget install Gyan.FFmpeg`):
```powershell
ffmpeg -i demo.mp4 -vf "fps=12,scale=960:-1:flags=lanczos,split[s0][s1];[s0]palettegen=max_colors=128[p];[s1][p]paletteuse" docs\demo.gif
```
Targets: 960 px wide, 10-12 fps, under 8 MB, about 60 s. If it is too big, trim idle time, lower the fps to 10, or reduce the width to 800.
GitHub shows GIFs inline in the README. For a longer MP4, you can drag the file into the README editor on GitHub (it uploads it and inserts the link for you), or attach it to a release. Do not invent a link: use the one GitHub or your video host gives you.

## 5. Put it in the README
```powershell
python scripts\gif_markdown.py
```
The script parses the GIF (size, frame count, duration) and prints the Markdown line only if it is a real, reasonable recording. Paste it into the **Demo** section of `README.md`
and delete the sentence "No recording has been made yet". The README test fails if the README embeds a file that does not exist.
